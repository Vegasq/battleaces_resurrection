REQUESTED USER FLOW
Connect to the configured community server. Custom Game -> Invite Friend lists
everyone connected to that server, with availability. Select an opponent; they
accept into the custom lobby. Both choose decks; the host starts from the custom
menu and the guest acknowledges before loading. Result/Continue returns to a usable
lobby for another game.
An existing Steam friendship is not required. This is a server-local directory,
not discovery of players on other servers or a replacement social network.

SERVER IMPLEMENTATION
Community control v1 separates presence from match seats. It publishes bounded
server-local directories, creates custom lobbies and handles targeted invitation
acceptance/decline/cancellation/expiry. Membership, host ownership, readiness and
decks are checked server-side, including simultaneous invite/departure races.
Host Start and a matching guest acknowledgement precede worker creation. Existing
validated room/worker execution is reused; results and RETURN permit same-socket
rematches. Ordinary protocol3 clients keep their existing behavior. TLS admission
also binds community sessions to authenticated profiles. See community-protocol.txt
for exact framing, bounds, timeouts, compatibility and verification evidence.

Fifteen community lifecycle tests and two added TLS identity tests pass. The real
simulation probe completed two custom matches with a changed deck and a third
uninvolved connected player. These scripted clients do not establish native Invite
Friend/Start UI operation; that translation and manual acceptance remain to do.
An isolated native adapter has since qualified Create/Leave and pending-create
cancellation/re-entry against the real coordinator, separately from those games.

NATIVE CLIENT FINDINGS (STATIC, NOT A WORKING UI IMPLEMENTATION)
The existing CustomGameLobbyManager and custom menu have lobby creation/update,
invitation and start plumbing. The friend picker currently enumerates
UncappedSteamFriends and checks Steamworks.Friend.IsPlayingThisGame. Inserting a
server roster into a list alone would still leave that Steam-dependent filter;
a dedicated roster/availability adapter must drive this UI.
FriendVM also calls Steam name/status/avatar APIs directly; use scoped native
property setters for community rows rather than assuming a display-name hook
covers every inlined access. Preserve native row pooling and lifetime.

StartGame RVA0x3cb1080 inlines TryStartGame and routes to SendUpdateAction0x3cac870.
Hooking only TryStartGame0x3cabc60 would miss the actual Start handler. Likewise
InviteToCustomGame0x3cabe80 inlines the front-service invitation wrapper and calls
EnqueueMessage0x256df90 at0x3cac066; a wrapper-method-only interception is incomplete.
Native start uses TryStartLobbyGame followed by ReadyToStartLobbyGame. Preserve
the native UI/request state machine while translating to the private server.

Deliver simulated native responses on a later Unity update: CreateLobby stores
its pending request after the front call returns; PartyInviteReplyRequest increments
its pending-response count after enqueue. An immediate callback inside either call
would run before native bookkeeping is ready. Exact ownership, request correlation,
timeout/cancel behavior and real callback ordering require runtime qualification.
