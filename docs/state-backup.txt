SERVER STATE SNAPSHOTS AND FRESH-LOCATION RESTORE
Updated:2026-10-17

Scope
P4 now has explicit backup, verify-backup and restore commands for saved decks
and hash-only invitation state. Stable identities, invite hashes, creation dates
and revocations survive restore. This is not a whole-machine backup: game assets,
client bearer-invite files, TLS private keys, host configuration, event logs and
native captures are excluded. Keep configuration/TLS keys separately protected;
import matching game assets on a replacement host. No game/helper code changed.

The snapshot/restore logic and real process-lock tests are automated. Real
protected-DACL deployment under the intended account, native restored-host play,
clean Windows and reboot/service acceptance remain distinct gates.

Commands
In a package, use BattleAces-Server.cmd backup --out <private snapshot path>,
verify-backup --input <snapshot>, and restore --input <snapshot> --destination
<new directory>. Each accepts --config; its default is config/host.json under
that package. The source equivalent is python -m server.state_backup with the
same command/options and an explicit --config. See windows-server-quickstart.txt
for complete operator examples and the subsequent check/start steps.

Host ownership and consistency
server.state_lock.exclusive_state holds a nonblocking OS lock on the one-byte
data/.host.lock for the packaged host/check lifetime, including worker and audit
cleanup. Backup takes that same lock before reading profiles/credentials. A
concurrent host/check/backup fails with an explicit stop-host message. Locks are
released by the OS after a process crash; there is no PID-based stale-file logic.
The lock file remains and must not be deleted/replaced while any host uses it.
An empty file left by interrupted first creation is initialized only after
acquiring the OS byte-range lock; it does not require deletion or a stale-PID
override. The actual Windows empty-file/concurrent-owner case passes.
No native worker or public listener starts before a host obtains this lock.

This is cooperative deployment locking, not a security boundary against an
administrator or unrelated processes. Legacy direct DedicatedServer/research
entry points do not take this data lock; do not run them against a deployed host
directory. Credential issue/revoke keeps its separate existing private store
lock, so export reads a coherent database while profiles are stopped. Later
revocations are not retroactively included in an existing snapshot.

Profile durability and validation
Saved profile schema1 is exactly schema,profile_id,deck. Reads are bounded to4KiB,
reject duplicate keys and require the stored identity to match the filename.
Decks pass the existing catalog/slot/ability validation. Profile keys use the
existing bounded ASCII protocol keys with Windows device names additionally
refused. Local profile files must be regular non-reparse files.

Save uses an exclusive random temporary file, flush/fsync and os.replace. Failed
write/flush/replace keeps the previous saved deck; only that operation's own
temporary file is cleaned up when permitted. This improves crash durability but
is not a claim about every storage controller's power-loss guarantees.

Snapshot format and output
The new file is bounded to4MiB and is ordinary JSON, not an archive to extract.
Envelope schema1 has exactly schema,payload,sha256. SHA256 covers the canonical
ASCII JSON payload (sorted keys, compact separators). It detects accidental
semantic changes; it is not a signature and does not authenticate an untrusted
replacement. Whole-file SHA256 is also returned for the owner's records.

Payload fields are created_at,compatibility,profiles,credentials. Compatibility
binds game build, asset format, game protocol, original GameAssembly hash,
simulation hash and a SHA256 of the verified asset-manifest file mapping. Current
assets are verified and loaded for deck validation before backup/restore. A
different asset export requires deliberate migration, not an unchecked restore.
Profiles map bounded IDs to eight-unit decks, with at most4096 records and no
case-folded Windows name collisions. The credentials member is the exact existing
schema1 hash-only database, or null for explicit loopback development. Secure and
development snapshot/config modes cannot be mixed. Database validation retains
its1MiB/4096-invite limits; no token-valued field is accepted.

Backup reads only committed profile JSON. Recognized old/new save temporaries
are excluded and left untouched. Unknown files, subdirectories, reparse entries,
bad profiles and excessive directory entries fail rather than silently dropping
data. CredentialStore.export_snapshot reads under the private database lock and
exports hashes/metadata only; client handoff files are never traversed.

The output is separate from live data/credentials/assets. It uses the existing
protected current-user/SYSTEM directory/file creation, exclusive creation,
flush/fsync and strict private readback. Existing output is never overwritten or
deleted. A failed new output is removed when possible; any inaccessible partial
copy stays private and permissions are never weakened for cleanup.
Both backup and restore reject destinations under the bundled program/app or
program/runtime before creating any output there.

Restore boundary
An explicitly selected transferred snapshot may have download-folder ACLs. It
is bounded and fully validated before any destination is created. It cannot
select filesystem paths: those come only from the operator's existing config and
the new destination. The destination must be absent and outside current live
data, credentials and imported assets. Even an existing empty directory fails.

Restore writes new data/profiles and data/private/credentials, preserving profile
IDs and the database's historical invite validity/revocations. A new empty store
is mandatory; import never replaces an existing database directory entry. Each
profile is read back and the private credential store re-parsed. A protected new
host.json is then validated and published last, exclusively. It keeps the chosen
config's host settings and absolute asset/TLS paths, with data/credential paths
redirected to the new directory. It does not start a server or alter the old config.
Failed restores retain their new incomplete directory for inspection with no
runnable host.json, and never recursively delete original or unrelated data.

On another Windows account, restore recreates private database files for that
account; do not weaken an old store's ACL to make it readable. Keep backups
private during transfer. Restoring an older snapshot can reactivate an invite
revoked later; review/reapply revocations before listening. A native host check
and real player connection/rematch are required after selecting the restored
configuration. TLS keys and original assets still need independent provisioning.
