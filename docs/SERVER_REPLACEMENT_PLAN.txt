1. OUTCOME AND SCOPE

Deliver a dedicated server that the owner can host on Windows x64,
plus a reversible patch and launcher that friends install into their existing
Windows game installation. Friends connect, create/join a private 1v1 room, select
their eight-unit decks, play a complete match, see the correct result, and play
again without restarting the game. The server remains available between matches.
The final client also starts and plays without any server. Public play can fall
back to local AI; Custom games guarantee human participants. The final-product
requirements below extend the initial 1v1 integration milestone.

Explicit requirements and decisions:
- Windows x64 server hosting; a patch for the Windows game client.
- Two clients on this PC remain the first integration test before other PCs.
- User-requested menu flows: Try Deck vs AI with the selected deck, and Custom
  Game -> Invite Friend showing players connected to this community server.
  Invite a chosen player, accept into the custom lobby, then start there.
- Normal play must not enable scripted production, automatic surrender, automatic
  Continue or automated rematch. Keep those diagnostic commands opt-in.
- Keep the research and implementation knowledge base current throughout.
- Client patch requirement added on 2026-10-17: remove outbound analytics and
  telemetry, including automatic crash-report uploads. Verify the relevant paths
  are disabled; this is planned work, not an already implemented capability.
- Put the project in git@github.com:Vegasq/battleaces_resurrection.git with
  dedicated locations for server source and client patch source/tooling.
- User confirmed on 2026-10-17 that the remote repository has been created and
  is waiting for its initial commit. Repository creation is no longer a task.
- User activated implementation of this plan on 2026-10-17, including the initial
  source-only commit/publication. Do not commit or push original client
  files unless an unavoidable dependency has first been demonstrated; default to
  local import/generation instead. No such exception is currently established.
- Scope revision on 2026-10-17: user removed Linux hosting entirely for now.
  This supersedes the earlier Wine decision. Linux/Wine work is outside this plan
  and is not a release requirement or a scheduled follow-up milestone.

Planning defaults:
- Friends may connect over the internet, not just the same LAN.
- Target the verified build and locally imported assets. The initial integration
  milestone is two-player 1v1; the final product also requires 2v2 and 2vAI.
  Trace their original maps, team/seat rules and AI setup before extending the
  current two-seat protocol. Multiple 1v1 rooms do not establish team-mode support.
- Windows x64 is the supported platform for both hosting and playing.
- Local and private profiles retain decks and cosmetic selections. Original
  account progression, commerce and ranked rating services remain separate work;
  public matchmaking with AI fallback is now in scope. No original account is
  required, and offline play must not require server enrollment or credentials.
- In-match reconnect is a later milestone. The first release must handle a
  disconnect clearly and return surviving clients to a usable lobby.

3. ARCHITECTURE DECISIONS

Use an authoritative simulation server: a "thick" server in gameplay terms.
Reuse the shipped simulation instead of reconstructing unit combat, pathfinding,
economy and abilities. Keep the existing custom protocol and client adaptation;
the client patch covers startup, profiles, lobby, gameplay and results, beyond
changing the original service URL. Original server internals remain unknown.

Proposed process layout:

  Patched Windows clients
           |
           | authenticated, encrypted connection
           v
  Windows server coordinator
    profiles / invites / rooms / readiness / input validation / match journal
           |
           | private, bounded, versioned IPC
           v
  One supervised simulation worker per active match
    exact Simulation.dll + trusted map/config + ordered inputs + native results

The coordinator and simulation workers run directly on Windows x64.

Keep the working Python implementation and native ABI as the starting point.
First isolate the existing Windows Python simulation wrapper in a child process;
package its runtime with the worker. Consider a small C++ host only if measured
packaging or execution problems warrant it. Worker isolation is for fault
containment and independent matches; no platform portability layer is required.

The coordinator owns external connections and validates client input. The worker
owns its native world, executes the ordered actions and reports state/result.
Clients receive only frames accepted by the worker. IPC carries match IDs, frame
numbers, payload bounds, errors and timeouts. Workers have no public listener.
Crash or hang of one worker must abort its match without stopping other rooms.

Preserve fixed 50 ms simulation steps. Configure input lead/buffering for network
latency without silently changing simulation time or dropping player commands.
Keep the native command validation and ownership checks across the IPC boundary.
