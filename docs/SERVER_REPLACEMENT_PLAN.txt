Planning defaults:
- Friends may connect over the internet, not just the same LAN.
- First release supports the verified build, existing 1v1 map and unit catalog.
- Each match has two players. Multiple independent rooms can serve more friends;
  this does not imply a team mode or more than two players in a match.
- Windows x64 is the supported platform for both hosting and playing.
- Private profiles retain decks; original account progression/store/ranked
  matchmaking are separate projects. No production account is required.
- In-match reconnect is a later milestone. The first release must handle a
  disconnect clearly and return surviving clients to a usable lobby.

Release acceptance, in user terms:
An owner installs the server package on a clean Windows host, imports the required
assets from their game installation, starts the service, and gives friends its
address and an invite. Two friends patch their own game copies, connect from
separate PCs, choose different decks, finish a match and rematch. The server runs
without the original services or a graphical server client.

3. ARCHITECTURE DECISIONS

Use an authoritative simulation server: a "thick" server in gameplay terms.
Reuse the shipped simulation instead of reconstructing unit combat, pathfinding,
economy and abilities. Keep the existing custom protocol and client adaptation;
the client patch covers startup, profiles, lobby, gameplay and results, beyond
changing the original service URL. Original server internals remain unknown.

Proposed process layout:

  Patched Windows clients
           |
           | authenticated, encrypted connection
           v
  Windows server coordinator
    profiles / invites / rooms / readiness / input validation / match journal
           |
           | private, bounded, versioned IPC
           v
  One supervised simulation worker per active match
    exact Simulation.dll + trusted map/config + ordered inputs + native results

The coordinator and simulation workers run directly on Windows x64.

Keep the working Python implementation and native ABI as the starting point.
First isolate the existing Windows Python simulation wrapper in a child process;
package its runtime with the worker. Consider a small C++ host only if measured
packaging or execution problems warrant it. Worker isolation is for fault
containment and independent matches; no platform portability layer is required.

The coordinator owns external connections and validates client input. The worker
owns its native world, executes the ordered actions and reports state/result.
Clients receive only frames accepted by the worker. IPC carries match IDs, frame
numbers, payload bounds, errors and timeouts. Workers have no public listener.
Crash or hang of one worker must abort its match without stopping other rooms.

Preserve fixed 50 ms simulation steps. Configure input lead/buffering for network
latency without silently changing simulation time or dropping player commands.
Keep the native command validation and ownership checks across the IPC boundary.

P3 - ENABLE PRIVATE INTERNET PLAY
Depends on P1/P2. Effort allowance: 4-7 days.
- Add authenticated, owner-issued and revocable player credentials; bind saved
  profiles to server-issued identities instead of a self-reported profile name.
- Protect the TCP connection with TLS using maintained TLS implementations.
  Document certificate trust/enrollment in the launcher, including a private-host
  option. Never solve certificate errors by disabling certificate validation.
- Keep secrets out of command lines and logs. Limit handshake rates, message size,
  pending joins and per-player queues; preserve existing command bounds.
- Add ping/connection status and configurable, bounded input buffering. Measure
  behavior at 50/100/200 ms RTT, jitter and packet loss before selecting defaults.
- PRIORITY: Investigate the reported unit lag in manual two-client play. Retain
  frame-delivery gaps and distinguish missing client inputs, Unity update stalls,
  worker/IPC time, audit I/O and render/presentation delay. Measure click-to-action
  latency as well as 20 Hz throughput; do not call a larger buffer a latency fix.
- Define stall handling: bounded wait, clear notice and an explicit aborted result
  when a connection cannot recover. Do not invent a victory for an unknown state.
- Support direct connection to an owner-hosted or rented server; document the
  one exposed service port and host-specific firewall/NAT setup. NAT traversal is
  not required for v1. A private VPN can be an interim test route.
Done when: two physical Windows PCs on different networks finish and rematch on
the Windows server; invalid/revoked credentials fail; injected network stalls
do not create silent divergence or leave clients stuck in a match.

5. ESTIMATE AND PRIORITY

Planning estimate for one experienced engineer: roughly 3-6 focused engineering
weeks from the current prototype to a packaged, private Windows server and client
patch release. This is an estimate, not a measured delivery date. It assumes
testing PCs/friends are available. Substantial client lifecycle discoveries or
networking issues require re-estimation. The narrower platform scope removes the
compatibility spike, second deployment package and duplicate platform validation.

The earlier estimate of days to a couple of weeks concerned a smaller Windows
local/LAN milestone. Internet transport, repeatable client
sessions and clean-machine installation add work to this requested release.

Critical order: baseline -> reusable server/client lifecycle
-> cross-PC internet acceptance -> packaging -> release playtest. Protocol and
documentation work can overlap implementation; defer optional UI polish and extra
modes until the complete play/rematch path is stable.

First implementation task after this plan: prepare, audit and push the initial
source-only commit to the existing remote, freezing the working two-client
baseline. Preserve captured replay
fixtures locally, then isolate simulation workers and make match cleanup and
room reuse reliable. The next user-visible milestone is a complete second match
with changed decks in the same two client processes on this PC.

Keep original binaries, game-derived inputs, generated output and private runtime
data outside tracked paths. Use ignored local directories for imported assets,
build output, profiles, captures and detailed test evidence. A small tracked

containing their contents.

Allowed baseline:

- Our architecture/protocol notes, research conclusions and implementation plan.
- Build hashes, offsets and narrowly scoped patch safety signatures where needed.
- Synthetic test inputs created for this project; test drivers that use optional
  locally supplied assets for full native integration.

Excluded from Git, including Git LFS and compressed/encoded copies:
- Battle Aces.exe, GameAssembly.dll, Simulation.dll, Unity/Steam libraries and
  any other shipped client files, whether original, backed up or patched.
- Battle Aces_Data, maps, textures, audio, game configuration and extracted game
  data. The current server/assets/build-37822 directory contains game-derived
  map/catalog/descriptor data and must not be copied into the repository wholesale.
- Metadata dumps, full decompilation/disassembly exports, packet/bootstrap/replay
  captures and game-derived test fixtures. Descriptors or catalogs extracted into
  JSON remain game-derived content even though their format is text.
- Compiled output, runtime logs, saved player data, credentials and local paths
  identifying the developer's environment.

Dependency strategy:
- The host/player supplies their existing compatible game installation locally.
- This workspace also has ../BattleAcesBeta_untouched for local recovery and
  pristine-input checks. It stays outside the repository and remains untouched.
- Import or generate required runtime inputs from that installation and verify
  hashes. Where extraction is not yet reproducible, document and implement the
  missing extraction step instead of committing the captured output.
- CI runs asset-free tests using synthetic data. Native integration tests clearly
  report missing local prerequisites; a skipped native test is not a native pass.
- Build the patch helper from our source and apply recipes to the user's local
  game. Release packages may contain our compiled helper, never a patched full
  GameAssembly.dll or embedded copies of game assets.

Before publishing each baseline/release:
- Review the exact staged file list and diff; scan for binaries, archives, large
  encoded arrays, embedded game payloads and secrets. Ignore rules alone are not
  sufficient because already tracked or force-added files can bypass them.
- Check the commits being pushed as well as the working tree, so removing a file
  in the latest commit does not conceal its presence in earlier history.
- Keep an automated content audit in CI to prevent accidental later inclusion.
- If an original-client-file dependency appears unavoidable, first document why
  import, extraction or a minimal patch recipe cannot replace it and identify the
  exact minimal content. Treat it as an explicit exception for user review before
  publication; do not silently widen the source-only scope.
