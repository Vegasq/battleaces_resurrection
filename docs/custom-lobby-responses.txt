PRINCIPAL FINDINGS
1. Host creation must feed ProcessCreateLobbyResponse; it always constructs an
   IsCreator=true custom Party. Guest acceptance needs its actual native
   PartyInviteReplyResponse followed by LobbyStateNotification. Notification
   alone never constructs Party; Update response is ignored when Party is null.
2. Native pending state is installed AFTER the enqueue hook returns. Queue all
   synthetic responses for the observed Unity update thread and correlate them
   with an owned native request, connection generation, lobby, and server ACK.
   A community LOBBY snapshot can precede ACK. Keep it as authority; do not turn
   it into an early native create acknowledgement from inside the hook.
3. An authoritative rejected update should normally use Error.GeneralFailure2
   plus the current valid snapshot. Error.Timeout1 retains and resends pending
   actions. Using timeout for a rejected START can create a retry loop.
4. Correction to the earlier custom-lobby-native.txt permission assertion:
   reviewed prediction and UI gates DO NOT consult LobbyPermissions. Host/local
   membership identity and role flags are the actual gates. Null permissions
   are explicitly accepted during prediction initialization, and native local
   create prediction itself leaves permissions null. A nonempty permission table
   is not an established requirement here. This is a bounded finding about the
   traced paths, not proof that no other code ever reads permissions.
5. Native player equality in manager prediction compares the complete named
   handle, including strings and unknown fields. Build a canonical named handle
   per community profile and use matching values everywhere. Existing per-match
   aliased seat identities must not silently replace stable lobby identities.
6. Native GameStart closure clears Party/current lobby/prediction. A durable
   server community room must survive separately in the adapter. Once native
   results/world cleanup finishes and the server room reopens, a state
   notification can reconstruct prediction and travel to the custom screen,
   provided Party and canonical identity have first been restored. That
   integration remains to be qualified.

CREATION, UPDATES, AND NATIVE CALLBACK SEMANTICS
ProcessCreateLobbyResponse RVA3e48360:
  void(front, CreateLobbyResponse message, Error error, MethodInfo*).
  Windows x64: RCX front, RDX message, R8D error, R9 metadata.
  Success allocates CustomGameLobby, installs message.lobbyState.lobbyState and
  permissions, writes front.CustomGameLobby and last custom mode, constructs
  Party(true, state.hostHandle, Custom3), updates matchmaking status, then raises
  Front.LobbyCreated(error). Failure raises LobbyCreated(error) without building
  a successful lobby. This is a HOST acknowledgement, never a guest shortcut.
  It does not independently raise Front.LobbyStateUpdated.

ProcessUpdateLobbyStateResponse RVA3e485f0:
  void(front, UpdateLobbyStateResponse message, Error error, MethodInfo*), same
  argument ABI. If front.Party or CustomGameLobby is null, it ignores the response
  and does NOT raise the response event. With an active party/lobby, message must
  exist. If its CurrentState wrapper exists, error0 installs the nested state;
  a nonzero error can also install a nonnull state whose status is greater than0.
  A success wrapper with a null nested state is invalid (dereferenced for mode).
  Permissions replace the previous value only when nonnull. It raises
  Front.UpdateLobbyStateResponse(error), then UpdateActiveLobbyStatus(error).
  It does not raise LobbyStateUpdated or update matchmaking status itself.

ProcessLobbyStateNotification RVA3e48820:
  void(front, LobbyStateNotification message, MethodInfo*), RCX/RDX/R8.
  With no Party, accepts only a state containing the raw local player handle;
  otherwise rejects as out-of-order. It never creates Party. It creates a
  CustomGameLobby wrapper if necessary, installs state/mode and nonnull
  permissions, raises LobbyStateUpdated, logs active status and updates
  matchmaking status. Direct handler does not use frontReceiver to route/check
  ownership; the adapter must validate it and deliver to the correct front.

OnLobbyStateUpdated RVA3cac9c0 validates/rebuilds prediction. In its EXISTING
prediction branch, state5 + exact local member + !host + Player role triggers
automatic native Ready case16 unless the current pending update request already
contains case16. It does not retain a separate acknowledged-ready epoch flag.
The NEW prediction branch initializes/clones state, tolerates null Permissions
at3cacf01..15, installs prediction and travels to the custom screen; it does NOT
run the Ready branch in the same call. Consequences for a scoped adapter:
  - If guest acceptance first observes an already-starting snapshot, schedule a
    later owned state update after initial prediction exists so native Ready runs.
  - After a Ready ACK clears pending, a repeated native state5 notification can
    generate Ready again. Track one ready decision per server start epoch and
    handle duplicate native requests without re-sending an invalid server command
    or stranding native pending state.
  - Do not project every community LOADING/RUNNING/RESULTS snapshot as a fresh
    native GameStarting notification. Maintain adapter authority separately.
  - Do not fake success for a START that the authoritative server rejected.

Suggested mapping, NOT runtime-qualified: server OPEN -> native Open1 with one
member or Full2 with two; server STARTING -> native GameStarting5 (host starts,
guest original Ready action acknowledges); loading uses the owned start state
until a fully validated bootstrap is ready. Runtime success must demonstrate
failure rollback and the late-guest/duplicate-snapshot cases above.

Manager.LeaveLobby RVA3cab820, when not already closed, builds case14 and directly

Proposed return strategy to qualify (original wire ordering was not captured):
  1. Keep durable community membership independently. Native GameStart3 closure
     should occur only for a committed, validated owned match transition, not
     merely host Start. Ensure original bootstrap/connection and closure event
     ordering cooperate before declaring it the final ordering.
  2. After native result/abort handling and actual world teardown/menu, send
     community RETURN for the exact completed/aborted match. A phase RESULTS
     snapshot alone must not bring the UI back while a native world is alive.
  3. Wait for authoritative OPEN, restore canonical lobby identity, build an
     appropriate custom Party from current membership/host, then deliver the
     state notification. It can rebuild prediction and travel to the custom UI.
  4. Guest restoration MUST NOT call ProcessPartyInviteReplyResponse again;
     there is no pending native invite reply and its counter would decrement.
     Host ProcessCreateLobbyResponse likewise forces creator semantics and
     creates a response event for a request that is not pending. Use controlled
     native Party construction plus notification if this strategy is selected.
  5. Qualify one player still in results, survivor after abort/disconnect,
     host transfer, setup failure before bootstrap, and fresh rematch epoch.

Existing ba::make/ba::call machinery can class-initialize, allocate, invoke

MessageExtensions.MergeFrom(IMessage, byte[]) for these owned message instances.
lan_transport.cpp's parse currently hardcodes GamePb; expand namespace/type
selection deliberately if using that construction route. Do not commit copied
descriptor/data tables, or raw client/metadata bytes to obtain these few shapes.

REMAINING IMPLEMENTATION / ACCEPTANCE GATES
- Native custom roster and invite row construction without inlined Steam calls;
  correct pending invite bookkeeping and native acceptance/decline presentation.
- Exact request-to-server command batching, selected deck synchronization, stale
  revision failure completion, unsupported mode/kick/move/promote handling.
- Stable lobby named identity across current seat-based bootstrap and teardown.
- Epoch deduplication, new-prediction Ready edge, rollback on timeout/rejection,
  duplicate callbacks, and late callbacks after Leave/Release/reconnect.
- Committed-start closure vs GameCreated/bootstrap order; never two worlds or
