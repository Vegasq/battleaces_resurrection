NETWORK DELAY QUALIFICATION
Updated:2026-10-17

The current protocol2 client queues three input batches and replenishes one after
each authoritative frame. The coordinator allows bounded contiguous lookahead
(MAX_AHEAD4), waits for both peers, and advances Simulation.dll by exactly50ms.
Its input-stall limit is10s. This is a small local pipeline, not a measured choice
for internet players. Configurable buffering and friend-facing connection status
remain P3 work. A match can stay deterministic while running slower than20Hz.

tools/run_secure_match.py accepts --rtt-ms0..500, --jitter-ms0..100 and a repeatable
--network-seed. For example append --rtt-ms100 --jitter-ms10 to the documented
secure two-client qualification command. Keep every run name unique. The optional
relay binds and forwards only IPv4 loopback; normal client/server code is unchanged.
TLS remains end to end with certificate/name verification and authentication.
The relay never decrypts, logs or persists application/ciphertext payloads.

Model: independent one-way stream-chunk delays of RTT/2 plus uniform +/- jitter.
Release times are clamped to preserve TCP byte order. Reading and scheduled writing
are separate, so successive chunks do not each incur cumulative whole-RTT waits.
There are at most8 concurrent connections,32 queued chunks of at most64KiB per
direction, bounded stream buffers,5s connect/write deadlines and owned shutdown.
This models delayed ordered delivery. It does not model remote TCP congestion,
packet reordering, packet loss/retransmission, bandwidth limits or actual internet
routing. Those remain physical-PC / controlled-network qualification requirements.

Five asset-free real-socket checks cover ordered large transfers with jitter,
measured round-trip delay, bounded connection admission/active shutdown, a peer-EOF
versus shutdown race, and invalid parameters.
Run: python -m unittest tests.test_stream_shaper -v
The native harness additionally verifies every completed match's exact input
receipts, sampled state and native result, and records each TLS authentication.
Its summary includes actual authoritative-frame cadence, p95/max interframe gap,
cadence-reset counts and relay counters. Completion success does not assert20Hz.

The200ms run's p95 interframe gaps were110.643/111.904ms, far above its50ms target.
The second match also included a3.398s maximum gap; its cause is not isolated.
At50/100ms there were occasional long gaps too. The large repeated cadence reset
count at200ms is consistent with the three-batch round-trip pipeline being too
short. It motivates bounded configurable input buffering and a before/after run;
it does not establish that every observed gap came from network delay. No default
or native/protocol change was made during this baseline measurement.

The jitter run used seed17. Its first lobby join was114s after server startup;

still logged native result delivery and exact legacy-modal release/navigation0
