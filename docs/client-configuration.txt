CLIENT CONNECTION CONFIGURATION - LOOPBACK DEVELOPMENT SCHEMA1

For authenticated encrypted connections, use the separate schema2 config and
Launch-SecureClient.ps1 described in secure-client-transport.txt. Its editable
server_host/server_port select the address, server_name/ca_bundle establish trust,
and credential_file selects the private owner-issued invite. That path requires
a compatible secure helper. Do not put an invite into the schema1 file below.

Each player has a personal client-config.json next to Launch-Client.ps1. The
server address is editable data; changing it never requires rebuilding the patch.
The example client-config.example.json is tracked. Personal configs are ignored
by Git because they contain a local installation path and persistent player ID.

Create your personal file once, from the source checkout:
  powershell -File client_patch/launcher/Initialize-ClientConfig.ps1 -GameDirectory "<your game folder>"

Then edit client_patch/launcher/client-config.json:
  server_host  IP address or DNS name of the friend's server; no http:// prefix
  server_port  listening TCP port; default 47623
  display_name your visible name (spaces allowed)
  room         same room key for the two players; letters/numbers/dash/underscore

Use 127.0.0.1 or localhost for the current two-client development test. DNS names
are resolved to IPv4 by the launcher. The endpoint remains configurable for the
remote-client transport milestone. IPv6-only hosts are not supported by this
schema1 development launcher.

Launch using that file:
  powershell -File client_patch/launcher/Launch-Client.ps1
Or select a different personal config explicitly:
  powershell -File client_patch/launcher/Launch-Client.ps1 -Config "<config path>"

Explicit command-line address/player/room settings override the corresponding
config values. -Slot 0/1 is retained for development probes and skips automatic
loading of the default config; normal players receive a seat from the server.

Initialize creates a random persistent player_id. Keep it across matches to keep
your saved deck. Each player must have a distinct ID; do not share your personal
config. This development protocol still uses self-reported profile identity.
The server supports authenticated TLS admission through the separate secure
launcher. Use the plaintext loopback development listener for this config version.
No credential is accepted by this config version or placed on a command line.

Development server:
  python -m server.dedicated_server --host 127.0.0.1 --port 47623 --assets "<assets>"
Plaintext binds outside numeric loopback are rejected. The experimental secured
listener requires certificate/key/store paths together; see admission.txt. Its
schema2 secure launcher can use it; this schema1 launcher cannot.
The configured endpoint is not sent to the original game services.

NORMAL TWO-CLIENT PLAY ON ONE PC
Use the patched installation and imported assets with the existing local runner:
  powershell -NoProfile -File tools/Run-LocalMatch.ps1 -GameDirectory "<patched game>" -AssetDirectory "<imported assets>" -RunName manual-play-01
Choose a fresh RunName for each launch. Select decks and press Play in both game
windows; Continue and the next Play are manual too. Keep the runner console open
while playing. Optional ClientConfig0/ClientConfig1 select personal configurations;
both configs must point to the runner's loopback address/port and the same room.

Do not pass Smoke, DeckSmoke, SurrenderSmoke, AutoReady or RematchSmoke for ordinary
play. SurrenderSmoke queues a native surrender at frame600 by default (30 seconds
of simulation time); it is a test command, not a dedicated-server match limit.
The helper checks this flag on every match, including rematches, so restart clients
without it to turn it off. Normal native victory/surrender rules remain in effect.
Detailed local state/receipt auditing is opt-in through -DiagnosticAudit on
Run-LocalMatch.ps1 (both server and clients) or Launch-Client.ps1 (client only).
Normal play omits this flag. Diagnostic snapshots run on the frame path; several
long pauses in the recorded manual test fell within that path. Server journals and basic logs
remain enabled. Runs without diagnostics cannot pass the full sampled-state/receipt
verifier. Secure automated qualification still explicitly enables its own audits.

On the development workstation, ignored local/Play Normal Match.cmd supplies the
tested installation/assets and existing player configs with all automation flags
omitted. Close the old visible test clients before double-clicking it; the earlier
Launch Updated Visible Test.cmd deliberately retains its automatic surrender test.

STANDALONE TRY DECK VS AI
Launch-Client.ps1 -OfflinePractice uses native local deck storage, simulation and
AI without a replacement server. tools/Run-PracticeMatch.ps1 -Config "<config>"
provides an ordinary visible session with no automatic surrender or Continue.
Use a settings-capable patched installation, open Settings -> General ->
AI Difficulty, choose Easy/Normal/Hard, then Edit Deck -> Try Deck vs AI.
The offline Settings Region row is reused; connected multiplayer keeps Region.
Changes apply to the next match and save automatically in the installation's
.battleaces-resurrection/practice-settings.ini. Select Normal to restore the
baseline; the original Settings Reset action does not reset this preference.
The optional personal config practice_ai_profile17/18/19 is the initial default.
A saved UI choice wins over it; explicit -PracticeAIProfile remains a diagnostic
override at startup. Older helper installations keep their earlier behavior.
See practice-difficulty.txt for the three levels and qualification limits.

EXPERIMENTAL NATIVE CUSTOM GAME
Install --community-experimental into an isolated working game copy, then add
-CommunityExperimental to Launch-Client.ps1 with a personal schema1 config.
For the local two-client runner, supply both ClientConfig0/ClientConfig1 and add
-CommunityExperimental; omit Slot/AutoReady/RematchSmoke. Existing server_host
and server_port config fields still select the server. Community presence has
no simulation seat until an accepted custom lobby starts. The schema1 room key
does not select a community lobby; Invite/Accept determines membership.

On this workstation, ignored local/Play Custom Match.cmd uses the experimental
copy and local/custom-play/player0.json and player1.json, on127.0.0.1:47631.
One player opens Custom Game -> Invite Friend and selects the other connected
player. Accept in the other window, then Start as host. Finish/surrender manually,
press Continue in both windows, and start another match from the restored lobby.
This launcher enables no automated gameplay, surrender, Continue or diagnostics.
Start/deck/return are automatically qualified; visible manual acceptance and
broader abort/departure handling remain open (native-custom-matches.txt).

Launch-SecureClient.ps1 also accepts -CommunityExperimental, or use Python
client_patch.transport.launcher --community-experimental with the existing
schema2 configuration. Both verify an experimental match manifest/helper before
launch. This retains TLS certificate/credential handling; no secrets are added
to game arguments. Native custom-match runtime qualification over that secure
path remains separate from the loopback native tests recorded here.
