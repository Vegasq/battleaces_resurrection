Local export and ownership
server_assets_export.cpp invokes the original mode1,2,5 builders sequentially.
The next mode starts on a later main-menu poll, after the previous intercepted
create callback has cleared its creating/front-root state. All three requests
are consumed locally; no match starts and no original server is contacted by
this path. Front identity is restored after every saved map and on failure.
The original team map has armies0,1,2,3 with alliances0,1,0,1. Its static builder
does not populate players or decks, so the export adds placeholder rosters/decks
while retaining the authored map, alliances and initial actions. Final server
construction replaces placeholders with the frozen actual roster.

The completion manifest is written last and declares map-1v1.pb.gz,
map-2v2.pb.gz,map-2vai.pb.gz,unit-catalog.json,ai-rules.json and bot-catalog.json.
raw_maps records each decompressed map's size/hash; legacy raw_game_data remains

decks. New team/bot members are all-or-nothing; old complete1v1 exports remain
usable for their original scope. Imported files stay private and ignored.

server_bot_catalog.cpp uses the original registered tables and deck serializer.
Shared decks are copied before serialization; selected ability order is retained.
Type1 character names come from CharacterName, without the editor GetName deck
suffix. Localization handles auto-release next frame, so the exporter converts
the boxed generic handle through its original implicit operator, acquires one
ResourceManager reference immediately, polls, copies the string and releases
exactly that reference. A managed GC root alone does not retain the operation.

CosmeticsUtils.AddCosmeticsEntitlements is static with arguments
(Cosmetics, ref List<CommonPb.Entitlement>, bool allowUnowned). The list MUST be
constructed first, as the original Deck.ToProtoRuntime does. The exporter finds
that exact closed list class through the reflected by-ref parameter, initializes
and roots it, then invokes the helper. The helper allocates entitlement entries
but does not create the list. allowUnowned=true avoids the ownership lookup; it
does not grant inventory or alter the character's equipped loadout. Effective
portrait/banner are identified from the emitted keys using original category
labels, including native default handling. Keys are Entitlement field3, not2.

Catalog schema1
The local JSON contains weighted opponent/teammate profile pools for modes1,2,4,5;
referenced profiles with original compatible decks; localized character identity
and full cosmetic entitlement messages; the installed English random-name pool;
allowed random portrait/banner IDs; all installed cosmetic IDs; and supported
practice strength triples. Character names use the exporting client's locale.
The validator rejects duplicate JSON keys, oversized inputs, unknown profile/
mode pairs, invalid decks, unsupported wire fields, missing cosmetic references
and invalid strengths. The file is bounded to4MiB; each deck to4KiB.

Replacement selection policy
server.bot_catalog.BotCatalog chooses a weighted enabled profile, then one of
its compatible decks. Type1 retains the original character name/full appearance;
other deck types use installed English names and allowed portrait/banner pools.
Names already in the match are excluded. Public strength is uniformly selected
from Easy,Normal,Hard independently of tactics and the saved Try Deck preference.
Explicit difficulty is available for practice/engineering callers. This policy
is new behavior; it does not claim recovery of the retired service's RNG.
Mode5 has no original teammate pool. The explicit replacement policy uses mode2
teammate profile59 for vacant allied seats and keeps mode5 character profile60
for opponents. Headless all-bot evidence below exercises this combination;
partial human groups and ordinary-client behavior still require qualification.

Frozen match construction
GameTemplate admits two armies for modes1/4 and four for2/5, requires contiguous
army IDs and original alternating alliances, and preserves that topology.
One GameData contains every participant. Frozen bot choices must agree with the
roster's identity, mode, profile and selected units; original deck bytes carry
active abilities/cosmetics, and army appearance agrees with the selection.
Frame assembly supports exactly two or four contiguous participant slots in
canonical order. This does not change the current two-body public FRAME protocol.

Strength values are ordinary int64 protobuf varints carrying Q32, not floats or
zigzag values. Normal leaves authored modifiers unchanged. Other strengths
compose resourcing with exact integer multiplication shifted32bits, retain
existing buffs and add multiplicative damage/health attributes. New modifier
keys are unique across original global modifiers, every army and all new bots.
Human modifiers are unchanged. Unit tests check sub-Q32 rounding and collisions.
