Updated:2026-10-17. Experimental Windows build37822 adapter.

STATUS
Start/Ready, the narrow original CustomGameCreated handoff and a same-connection
result/return prototype are implemented. The first automated two-native-client
two-match flow passes, including duplicate requests, a changed deck, definitive
Start rejection and an expired attempt with a late Ready ACK. The normal

The existing native request enqueue hooks cover both the visible main-screen
StartGame3cb1080 inline path and the manager's own TryStart. Update action15 is
TryStartLobbyGame; action16 is ReadyToStartLobbyGame. Native builders allocate
empty payloads even though the protobuf types have deck/cosmetics fields.
The adapter reads the real selected deck separately and validates it.

Native SendUpdateAction3cac870 and SendUpdateActions3cad560 assign the returned
request to manager._pendingLobbyUpdateRequest only AFTER enqueue returns, at
3cac8e4 and3cad6db respectively. Responses must therefore be deferred and matched
to the exact rooted native request/manager in the live front session.

ProcessUpdateLobbyStateResponse3e485f0 is void(front,message,error,MethodInfo).
Its response.currentState is FrontPb.LobbyStateNotification, whose lobbyState
is CommonPb.LobbyState. A wrapper with a null nested state is unsafe, including
on some failure paths. Error0 and GeneralFailure2 release the old pending request;
Timeout1 retains/retries it. The response event carries only Error, not request ID.
SendUpdateActions runs synchronously and may enqueue a NEW native request before
the callback returns. Its postcondition is old-request relinquishment, not that
the pending pointer must remain null. Batched repeated actions are possible.

OnLobbyStateUpdated3cac9c0 automatically emits guest Ready for status5 when an
existing prediction identifies the local nonhost player. Suppression examines
only the current pending request's case16 actions; no persistent acknowledged
epoch flag exists. The first-prediction branch initializes/navigates but does not
emit Ready. Replaying status5 after an ACK can otherwise issue another Ready.

No expiry read was found in the traced Start/Ready/prediction/notification paths.
Original Start predicts status5 without setting the expiry field. The custom
main-screen VM has no countdown field, and its notification hides on status4/5.
This bounded evidence supports leaving expiry at its default for this prototype;
it is not proof against every indirect/reflection consumer. Any future displayed
countdown must come from an authoritative remaining duration and attempt epoch.

HANDOFF ORDER
ProcessCustomGameCreatedNotification3e40410 is void(front,message,error,MI).
On success it posts JoiningGameSignal, calls GameServerIntegration.JoinGame,
updates matchmaking status, then raises CustomGameCreated. The notification's
playerHandle does not establish ownership. The adapter must validate that itself.
Only its exact JoinGame call is redirected:
  RVA3e405e3, raw3e3ebe3, original bytes e858330100, original target3e53940.
  ABI void(server,GameConnectionInfo,bool spectator,MI), Windows RCX/RDX/R8B/R9.
  Non-community invocation forwards unchanged to the original target.

The adapter waits for assigned-seat WELCOME31, MATCH_INFO32, frozen BOOTSTRAP12
and an ordered community LOADING snapshot containing the same match ID/epoch.
Earlier Starting/Loading snapshots can precede the match ID; bootstrap globals
can be populated while earlier control events are still queued. Native request
ACK ownership must also be settled before starting the world.

Within one adapter update, while canonical community identity is still present:
1. Deliver original CustomGameCreated. The narrow Join hook only captures exact
   expected server/connection/non-spectator ownership. Let the outer native
   status/event tail finish before changing any identity.
2. Deliver original LobbyClosed3e48ad0 with GameStart3 and let all events finish.
   The manager releases prediction; the screen's Leave/GoBack callback then sees
   no active prediction and does not send a duplicate community Leave.
3. Switch to temporary aliased simulation handles1/2 and run existing beginJoined,
   which supplies the original ProcessJoinedGame/map/simulation bootstrap.

JoiningGameSignal records intent for the next native state Update. Joining state
polls HasActiveGameConnectionInfo; leaving a frame gap without it can return to
menu. The capture, original callback tails, closure and bootstrap therefore all
finish before this adapter update yields.

Front.JoinedGame3e3e050 sends online/Steam presence but writes no local Front
in-game flag. Suppressing that obsolete transport callback does not lose a local
flag. Native ProcessJoinedGame still owns its game-server lifecycle fields/events.
MatchDataManager initially derives IsCustomGame from received GameConfig; existing
dedicated_results sets the private-match result flag before EndOfGameResponse.
Do not alter received bootstrap bytes after their authoritative hash is frozen.

ADAPTER POLICY
Open maps to native status1/2 by membership. Starting maps to5. Loading/Running/
Results do not generate new Starting notifications. Repeated revisions coalesce;
a late first Starting projection receives one extra original notification to
enter the Ready branch. Per-lobby/epoch decisions suppress duplicate wire Start/
Ready, while each newly retained native request receives its own completion.

Host Start waits for earlier deck edits, submits a differing selected deck for
validation, then sends the current lobby revision. A guest whose current selected
deck differs from the frozen attempt cancels readiness rather than silently
playing a different deck. Definitive rejection uses error2 with current authority.

After original result Continue and actual native world teardown, the match-only
reset clears simulation/input/bootstrap/result/seat state while preserving the
community socket, ordered control events, request counter, identity cache and
deck service. RETURN names the exact finished match. Only authoritative Open
restores the same native Party/canonical profile and feeds LobbyStateUpdated to
reinitialize prediction. It does not fabricate a Create or invitation-reply ACK.
