VERDICT AND BOUNDARY
Presentation-only FriendVM children (strategy A) are supported by the inspected
prefab bindings for the custom invite row and recipient custom-invite popup.
Neither IsModelSet nor ShouldShowFriend controls visibility in these prefabs.
Native setters can render the children while IsModelSet remains false, without
calling FriendModel/Steam. Keep ORIGINAL outer row binding and native popup model.
Do not forward owned child bindings to the original FriendVM.set_Model first.

This is a bounded implementation recommendation, not graphical runtime proof.
Every owned bind must repaint all relevant properties and call UpdateAllBindings.
For a freshly acquired popup this may require a deferred flush: root Initialize
can bind before its child BindingCollections initialize. See the order below.
The native no-candidate/lookup-failure branch does not erase old presentation;
clear BOTH owned popup children explicitly when an owned lookup fails. Preserve
the native outer notification lifecycle: None0 and InCustomLobby11 release the
popup. Dropping only the child model does not hide its GameObject or clear text.
Keep unsupported child invite/profile/spectate actions disabled. No global Steam
friend cache, shared localization descriptor, or prefab mutation is needed.

MODEL / SETTER / POOL LIFETIME
Exact model namespaces: Uncapped.UI.FriendModel#3382 and
Uncapped.UI.FriendExtension#3380. FriendModel has NO noarg ctor. Its original
ctor takes ref Steamworks.Friend,bool and calls Steam-dependent extension update;
use the separately reviewed owned constructor strategy, not ba::make with .ctor0.
FriendExtension has an ordinary noarg ctor. The row model stays rooted and uses
canonical PlayerHandleWithName values. The presentation child remains unbound.

FriendVM public setters do not call Steam or require IsModelSet. Normal setters
call binding-aware ViewModel.Set -> ViewModel.UpdateBindings3d6a240 ->
BindingCollection.Update3af89e0. The collection's own _initialized flag gates
notification. Native pool Initialize initializes those bindings even if no child
model is set. Same-value setters may not notify: call UpdateAllBindings3d699d0
AFTER repainting the owned child, not just for the first field that changes.

Initialization ordering is different for the row and popup. Pool OnTakeFromPool
calls Owner.Initialize at3d5be92; it completes all initialize handlers before
GameObject.SetActive(true) at3d5befd and returns. The roster row's later outer
model bind is therefore after child binding initialization. Popup root Initialize
3d24610 calls set_Model/Refresh at3d246c4 while Owner is still walking its handler
array. Its child FriendVM may not be initialized yet. The generic native
get_UpdateBindingsPostInitialize resolves to6d5ba0 (false), so the child's later
Initialize does NOT guarantee UpdateAllBindings. A first setter write can be
stored but never rendered. Keep an owned pending presentation/flush, re-resolve
the same owner/session/children on the next Unity update, require both child
BindingCollection.get_Initialized, repaint then call UpdateAllBindings. Drop the
pending record on release. Do not rely on a later native Refresh, same-value
setters, or forged IsModelSet/initialization flags. Actual handler array ordering
was not observed; the guard handles that uncertainty.

Do not forge IsModelSet=true. Require the exact child and active owner/session,
initialized child and binding collection. If previously model-bound, original
ClearModel performs observer detachment without calling FriendVM.Refresh; confirm
IsModelSet=false before taking presentation-only ownership. ClearModel may leave
base _model nonnull. That is not an active observer or a safe ownership token.

No-invite branch3d25a68..3d25aee directly clears IsModelSet and unobserves only
when the flag was true. It does not clear _model, text, portrait, action flags or
ShouldShowFriend. FriendVM has no own Release override. Base ViewModel.Release

leaves presentation backing values. Repaint every reused child. Do not trust old
property values because the pool returned the same object address.

Row picker Release3ca95f0 first ClearInvitableFriendsList3ca98e0 (ordinary pool
release of each row), then unsubscribes FriendsChanged and PredictedLobbyChanged,
then tails ViewModel.Release. Pool OnReturnedToPool3d5bb70 calls the owner's
lifecycle release and deactivates the row GameObject when the container does not.
The dialog uses UIContainer with DisableCanvasWhenHidden=1 and
DisableGraphicRaycasterWhenHidden=1; Cancel targets UINavigationBack.Back.
Thus Escape/Cancel should use native owner/pool release, not an adapter Destroy.

expecting bindings to update. Re-resolve/validate owner, child initialization and
session generation before every use regardless of which boundary is selected.

OUTER ROW FALSE INVITE GUARD (SOURCE REVIEW FOLLOW-UP)
The roster-only adapter's false CanInvite value reaches the native button on
normal first bind/reuse. Shared generic ModelUpdated29b93a0 takes IsModelSet=false
path, stores model and true flag, ensures bindings, then UpdateAll at29b9476 BEFORE

the later same-false setter suppresses a change. If a pooled row retained true,
the initial flush sends true and guarded setter changes it false before bind

UpdateAll and no need to invent one for this normal Take->Bind path. Actual
UIButton.interactable still belongs in smoke evidence; skipped Release or
out-of-band receiver mutation is outside this guarantee.

SOURCE REVIEW FINDING / RESOLUTION
An initial population catch released a failed unlisted native row after adding
its ownership record, leaving a stale rooted record able to claim pool reuse.
The parent subsequently removed that record before release and added native
Clear of the successfully listed prefix on outer failure. Reviewed read-only.
No other concrete call/tail ABI or non-community fallback defect was found in
the roster-only slice. The wrapper is at a post-Clear screen release tail, so
its presentation reset writes retained backing values after child bindings have
released; the initialized guard prevents its explicit UpdateAll. Normal next
acquire fully repaints. A hypothetical duplicated live screen/listener remains
an untested ambiguity: mainScreen currently chooses the first exact live target;
reject multiple distinct candidates if this resolver is promoted beyond smoke.
