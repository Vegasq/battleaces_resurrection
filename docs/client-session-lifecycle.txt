CONTRACT

A TCP connection represents one lobby and at most one match. The Unity process,
local profile and native menu/deck editor survive across connections. This is
lobby re-entry, not reconnect/catch-up to a running native world.

The client sends HELLO21 with the existing layout and version3 in its u16 field:
preferred seat u8, original GameAssembly SHA256, Simulation SHA256, then three
u16le-length UTF-8 strings (profile, display name, room). Preferred seat 255 asks
the server for the first free seat; explicit -lan-slot=0/1 remains available for
controlled probes. Protocol3 S_WELCOME31 contains the assigned seat0/1,a server-
selected2..12-frame input window,and32 deck bytes. Both seats use the same frozen
window; native menu reset clears it before a new WELCOME. See protocol-v3.txt.
An auto-seat connection requires a stable explicit -player-id. Profile identity
must not derive from the assigned seat. Without an explicit seat, native logs
are dedicated-native-PID.log rather than a shared slot filename.

No native army/player identity is installed before WELCOME. The assigned seat
drives the current private alias ID (seat+1), JoinArmy and local army. Current
native player labels remain LAN Player1/2, matching the existing bootstrap
identity convention; the HELLO profile/display name has separate server scope.
WELCOME for a fresh connection may assign a different seat from the prior match.

The shared argument reader now tokenizes Windows quoting and matches exact
option keys. Both -player-name="Player One" and "-player-name=Player One" retain
spaces. UTF-16 values are converted strictly to UTF-8; another argument's value
cannot impersonate -room= or -player-id=. An asset-free command_line_tests.cpp
exercises those cases, Unicode, escaped quotes/backslashes and absent options.

Each new match requires a new S_MATCH_INFO32 ID, canonical S_BOOTSTRAP12,
SHA256 C_LOADED3 barrier and S_START13. Input and frame sequences restart at0;
the first three input batches are submitted again. Frozen decks, JoinArmy at
frame0 and identity validation remain enforced by the server. No client publish
message or new reset/epoch message is introduced.

After authoritative S_MATCH_END36, the existing result adapter checks the native
winner and invokes the original EndOfGameResponse path. Native victory/defeat,
post-game and Continue own their ordinary lifetime. A clean server FIN after a
complete S36 does not cancel pending results; all buffered packets are parsed
before FIN is interpreted. A partial final packet or EOF before S36 is an error.

After user Continue, dedicated_adapter.cpp requires ALL of:
  - the current native FSM is the owner's MainMenu state;
  - a native world was observed for this session;
  - Simulation._simulationIsActive is false and _world is zero;
  - GameServerIntegration._mapLoadInProgress is false.
It then resets helper state and connects again after500ms. No native world is
freed by pointer manipulation, the default mode does not advance result UI, and
no old input or bootstrap crosses the new connection.

The coordinator must retire completed rooms from the active room-name registry
while keeping old result sockets separate. One player can then Continue into a
new lobby while the other is still viewing old results. A closed old socket must
release that profile reservation. Old-room cleanup must not delete a new room
with the same name. Shutdown/resource bounds must also cover retired rooms.
Old result sockets may expire after a bounded wait; this does not prevent later
native Continue. Fresh room readiness starts empty and never inherits old ready.

RESET OWNERSHIP

The Unity front-update thread owns connection reads and lifecycle transitions.
The adapter checks its thread ID. Native simulation shutdown joins the worker
before the idle-world boundary. The helper disables command capture before
clearing both input queues under the existing queue lock.

Reset closes the socket and balances WSAStartup/WSACleanup; clears receive/send
buffers, pending frames, loaded bootstrap/hash, match ID, saved welcome deck,
ready/start/end flags, frame counter and the initial-input-pipeline flag; frees
the helper server/front/account GC handles; resets local-input clocks/counters,
bootstrap flags, normal-build smoke plan and result pending/delivered metadata.
Old front/server PlayerGameHandle references are cleared before a new WELCOME.
Original Unity systems, profile/progression, native UI objects and server-saved
deck remain owned by their existing lifetimes. Native match creation initializes
the next world and match data through the same ProcessJoinedGame path as before.

The one-shot dedicated front flags were replaced by the new adapter. Legacy LAN
and offline tutorial paths retain their existing behavior. Explicit asset export
still suppresses dedicated networking. -dedicated-server alone enables the
adapter; -offline-lan is retained for backwards-compatible launchers.

ERROR AND RETRY BOUNDARIES

Connection/WELCOME timeout is15 seconds in development TCP mode and30 seconds
through the secure bridge. A transport/bootstrap/input error stops
helper input and closes the connection. After a finished map load with an active
world, the adapter calls original CleanupGameState(reason1,skipShutdown=false)
once. Its native shutdown path returns to menu, stops/joins the simulation and
destroys the world. This is an abort, never a synthesized winner or S36 result.

The adapter will not cancel a native async map callback by clearing its flags.
It waits until loading finishes before requesting cleanup. If a callback never
finishes or safe native teardown is not observed within120 seconds, it retains
the old state and logs that a process restart is needed. This limitation remains
a failed-load UX/lifecycle gap, not a claim that every loading failure recovers.

Once safely at menu, connection errors have at most three automatic retries,
with1/2/4-second delays. Native Play can request another retry after exhaustion.
A failed attempt does not automatically ready the room unless Play requested it.
The current error presentation is local logging/native queue cancellation;
friend-facing inline error text and retry controls are still separate P2 work.

Test flags remain opt-in. -dedicated-auto-ready readies the first match only.
Add -dedicated-auto-rematch to also ready after each manual Continue. Neither
flag alone closes the post-game screen. -dedicated-rematch-smoke additionally
automates Continue after the FIRST native result, then performs one distinct,
native-validated core-slot edit on the second lobby's saved deck. Use all three
flags together to automate two matches. The smoke flag caps auto-ready at TWO
started matches and leaves the second result screen open. It does not modify
world state, bypass native validation or invoke a top-level FSM transition.

The smoke waits for inactive/zero world, native RGamePostGameState, active
UIPostGameController.MatchResultState, a live MatchResultVM and an empty native
navigation stack, then waits2 seconds and invokes MatchResultVM.OnContinue once.
Logs explicitly label that call as automated, NOT manual UI input. The second
deck edit chooses a different, nonduplicate core unit from a short probe list,
calls original IsValidSlot, Deck.set_Item and AutoAssignAbilities, and requires
the existing save callback plus full native deck validation before auto-ready.
The ordinary first-deck smoke setter test remains a one-time process probe.

PER-MATCH LOCAL EVIDENCE

With -lan-audit, each dedicated match writes these game-side runtime files:
  lan-audit-PID-MATCHID.tsv       existing observable-state audit columns
  lan-resources-PID-MATCHID.tsv   existing army-resource columns
  dedicated-receipts-PID-MATCHID.tsv
      tab-separated header: pid, match, frame, actions, sim, sha256
      one flushed row per received/applied complete frame; digest is SHA256 of
      the entire S_FRAME payload (frame u32, length0 u32, input0, input1)
  dedicated-bootstrap-PID-MATCHID.pb.gz

MATCHID is the32-character server ID. Both TSV audit schemas retain their old
columns and two fixed viewers; samples from different matches never share a
match-specific file. The legacy lan-audit-PID.tsv and lan-resources-PID.tsv mirror
FIRST match only, preserving old single-match probes without duplicate frames.
The legacy lan-bootstrap-PID.pb.gz remains a latest-match convenience copy.
Optional raw frame dumps also contain MATCHID. The worker receives a copied
match label published under an SRW lock BEFORE native world startup. It never
reads a concurrently mutated transport string. A reused native world address or
worker thread cannot select the old file because the match label is independent.
Main-thread frame receipt logs also append match=ID. All captures stay local.

COMPLETED-MATCH LEGACY DISCONNECT DIALOG

In the manually launched p2-visible01 pair, both visible windows showed
"CONNECTION ISSUE / You have been disconnected / RECONNECT / QUIT TO DESKTOP"
over the native results screen. Both simulations had already reached an inactive,
zero world and RGamePostGameState; the navigation stack contained one item.
The first recorded blocked state preceded the dedicated socket's graceful EOF
by about50 seconds. Coordinator evidence contained620 frames and complete client
receipts,62 sampled views per client, zero state mismatches and zero server errors.
This establishes a real UI blocker after a valid match, not a coordinator failure.

Static trace in the supported original identifies the obsolete service path:
  UILoginFlowController.OnStartJoiningGame RVA0x3d07010 sets game tracking=true
      and hides front-service reconnection UI while the native match is active.
  OnGameStateCleanedUp RVA0x3d07020 clears tracking, reads the original
      FrontServerIntegration connection status at+0x118 and calls UpdateView.
  UpdateView RVA0x3d07280 selects _disconnectedModal(+0x98) when status=0,
      unless the original service reports a distinct maintenance/idle condition.
  ShowModal RVA0x3d07390 records that descriptor in _activeShowUIObject(+0x78)
      and the native UI object in _activeModal(+0x70).
The dedicated adapter owns a separate socket; the intentionally unused original
front service remains disconnected. The other controller, UIGameConnectionStatus,
does the opposite during cleanup: RVA0x3c899d0 stops its reconnect flow and hides
its game-connection modal. Local trace files are disconnect-ui-types.json and
legacy-login-disconnect.asm under investigation/dedicated outside this repository.

The adapter therefore makes at most ONE original UILoginFlowController.
HideReconnectUI call per match, only after all of these conditions hold:
  - matching authoritative S36 was delivered after local native winner validation;
  - this session observed a real active world, now inactive/zero, in native postgame;
  - transport/input are healthy, failureReason is empty, and packet polling has run;
  - the exact login controller is found through its GameStateCleanedUp delegate,
    references this front/server pair, has stopped game tracking, and front status=0;
  - _activeShowUIObject is exactly its own nonnull _disconnectedModal descriptor,
    with a live _activeModal. No generic modal type or navigation-count shortcut.
The controller search is bounded to120 checks at250ms intervals while eligible.
The release-attempt flag is set BEFORE the call. Inspection/release failure logs
once and never retries. The flag resets only at the existing safe menu/world reset.

HideReconnectUI RVA0x3d079c0 cancels its own disconnect coroutine and invokes
HideExistingModal RVA0x3d078c0, which releases that object through the original
IUIObjectPool. Normal UI release handlers own navigation removal. The helper does
not clear/pop the navigation stack, change a connection-status field, fabricate
an input event, replace any cleanup subscriber, or force a postgame transition.
Other dialogs and all unsuccessful dedicated match paths are untouched. A later
real coordinator ERROR still stops the helper and enters ordinary error recovery;
there is no repeated modal suppression. Current dedicated failure presentation
remains the separately documented logging/native cancellation UX limitation.

Runtime proof requires the exact controller and matching descriptor, navigation
count before/after original release, and a second match in the same processes.
The coordinator results below establish those automated checks. Manual Continue
remains a separate acceptance check. The code logs the precondition and
post-release native references/count with the match ID.

Prior runtime evidence, before this rematch change: dedicated06 and dedicated07
