ADMISSION AND IDENTITY
Use the community v1 HELLO after the existing TLS admission. A queue ticket is a
nonzero u64, strictly increasing per authenticated session. Reconnecting creates
a new session; the graphical adapter must also reject callbacks from the old
connection generation. Names come from the admitted community session, never from
another player's queue packet. The selected eight-unit deck is validated and
frozen at ENTER; another deck mutation cannot alter that search's eventual match.
All commands share community request IDs, rate limiting and ACK53. Valid stale
state requests receive a negative ACK; malformed wire/request IDs close the peer.
The existing community directory cap remains136. The connection limit is now
min(136, max_rooms*4+8), allowing four humans per active room within that cap.

WIRE
Outer framing is unchanged: u32 body length, u8 message type, payload;2 MiB cap.
Integers are little-endian. Text is u16 byte length plus strict UTF8; keys use the
existing1..48 ASCII letter/digit/underscore/hyphen rules. Deck is8*u32 unit IDs.
Every queue command starts with u32 request, u16 queueVersion=1, u64 ticket:
  58 ENTER   u8 mode, u32 remainingWaitMs, deck
  59 CANCEL  no additional fields
  60 READY   text proposal key
  61 RETURN  text completed/aborted match key
Command payloads are14..256 bytes; ENTER is51 bytes. remainingWaitMs is0..30000,
including time already spent establishing the optional connection. The client
must measure that original search deadline monotonically and must not reset it
on connection success or reoffer. Supported modes are1,2,5; practice mode4 does
not enter a public queue.

Server packets:
  62 STATE   u16 version, u64 ticket, u8 phase, u8 mode, u32 elapsedMs,
             text proposal/match key or empty, text reason (at most128 bytes)
  63 MATCH   u16 version, u64 ticket, u8 mode, u8 participantCount, u8 slot,
             u8 humanMask, u8 inputWindow, text match key, deck
  64 FRAME   u32 frame, u8 participantCount; for every slot in ascending order:
             u32 inputLength, inputLength canonical PlayerInputActions bytes
STATE phases:0 waiting,1 offered,2 preparing,3 loading,4 running,5 results,6 retired.
MATCH inputWindow remains2..12. Mode1 has2 participants and human seats0/1.
Mode2 has4 participants and human seats0/1/2/3. Mode5 has4 participants and human
seats0/2; humanMask must contain the assigned seat and no prohibited seat.
FRAME count must match MATCH; each input is1..65536 bytes. Every seat has an
explicit length, with no implicit final remainder. Frame numbers are0..2^31-1.
The largest four-seat frame payload is262165 bytes. Reject count mismatch,
truncation, zero/oversized inputs and trailing bytes before constructing objects.

Legacy WELCOME/MATCH_INFO/FRAME packets are not emitted for a public match. A
public assignment precedes the existing BOOTSTRAP12; LOADED3, INPUT4, START13
and MATCH_END36 retain their existing formats (see protocol-v3.txt). Only opted-in
queue clients receive types62..64. Old community clients can still use Custom.
Snapshots and assignments can precede their command ACK; do not assume lockstep.

ARBITRATION AND TEAM ASSIGNMENT
Waiting is ordered by original search entry time, then profile key. A full human
roster is offered immediately. At the oldest waiting player's30-second deadline,
the coordinator offers the available group and fills vacancies with bots after
commit. Mode2 assigns humans0,1,2,3 in order; allies remain0/2 versus1/3. Mode5
assigns humans0,2 and always reserves opponents1,3 for bots. A solo mode5 player
gets an AI ally in2 using the documented original mode2 teammate pool.

Every selected human must READY the exact proposal before its10-second offer
deadline. A proposal reserves one room-capacity unit but creates no worker yet.
The final READY is the single commit point: phase becomes PREPARING before the
launch task is scheduled. Duplicate/old READY cannot start another worker. Bot
deck, name, portrait, banner, profile and supported random difficulty are frozen
once at commit by BotCatalog; practice difficulty never controls this choice.
All humans and bots then share one GameData, one authoritative worker, one input
stream and one result. The worker cannot replace a human slot with bot input.

CANCEL is allowed while WAITING/OFFERED. Cancelling an offered player dissolves
that proposal and requeues surviving players with their original deadlines.
On offer expiry, nonresponders retire; acknowledged survivors requeue without a
fresh30-second wait. READY itself checks expiry, even before maintenance runs.
No acknowledgement means no worker/bootstrap. Custom/practice/invitations and
deck changes cannot overlap an active public ticket.

After commit, cancellation is rejected. The client must show accepted-match
preparation and retain ownership through loading/results or explicit failure.
Setup failure before assignment publication retires tickets and releases seats,
including evidence-file failure after the native worker has initialized. Once
assignment delivery begins, a later error retains the match ID through aborted
RESULTS/RETURN, even if some players never receive assignment or BOOTSTRAP.
Clients must settle that proposal without requiring a native world to exist.
Disconnect during delayed creation closes a worker even if creation returns
after retirement. A disconnect from an active shared match aborts it; surviving
community sockets stay available for explicit recovery/RETURN. Results free
global room capacity immediately; each participant releases its ticket and old
peer slot independently with RETURN before queueing again.

At room-capacity exhaustion, expired waiting tickets retire with an explicit
reason; no worker is silently overcommitted. Client handling of that retirement
is part of the pending availability/fallback integration, not a completed UX.
