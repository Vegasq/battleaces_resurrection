SCOPE AND LAYOUT

P4 implementation can proceed alongside unresolved P3 acceptance. These archives
are development previews, not a completed friend-play release. The server and
client are separate packages; neither includes original game files. The client
includes only our helper DLL, patch recipes, transport and launch commands.
Game build37822 / protocol3 / community protocol1 / asset format1 / patch schema2
are distinct compatibility fields. Package version remains0.2.0-dev.

Each archive has program/runtime (bundled Python), program/app (explicit source
allowlist), config and QUICKSTART.txt. Server assets and writable data live beside
program/. The client helper is program/client-helper/BattleAcesOffline.dll.
Program paths are immutable during operation; host config rejects asset/data/TLS
paths inside either the bundled application or Python runtime. Relative host and
client config paths resolve from the config file, not the terminal directory.

Use docs/windows-server-quickstart.txt and windows-client-quickstart.txt for the
commands copied verbatim into the packages. No firewall changes, dependency
installer, global PATH changes or game downloads are performed by these tools.
Manual practice retains no automatic Play/surrender/capture flags. Secure launch
keeps private invite contents out of the command line.
The client CMD now opens Connection Setup when double-clicked. It confirms the
host's exact public CA file hash, imports transferred invites into protected local
copies, saves schema2 config and checks TLS/AUTH before launch. Runtime private
read checks remain strict; see client-enrollment.txt for scope and acceptance.

Committed source is required by default. --allow-dirty explicitly creates a local
preview with dirty:true, source revision and per-file content hashes. It is not
evidence that a particular commit contains every packaged byte.

The builder verifies the runtime's complete pinned SHA256 before extraction.
Archive path/type/size bounds reject traversal, device names, alternate streams,
normalized names, links and case-folded duplicates. Only reviewed source paths
are copied, and they also pass the source-content audit. The helper must be an
AMD64 PE DLL with the current protocol, practice, difficulty and loading markers.
Those markers are compatibility checks, not proof of a compiler/source match.
Only the supplied authored helper is included; no game installation is traversed.

Output must be fresh/empty. Failed builds remain for inspection. Fixed timestamps
and sorted entries make identical inputs/source state under the same build
toolchain produce identical ZIPs.
build-report.json records archive SHA256s; each package contains compatibility
and per-file integrity manifests. Verification detects missing/changed files and
unlisted program files, while allowing personal config/assets/data. These local
hashes are not code signing or an authenticity boundary against a hostile package.
Archives/runtime/helper binaries stay ignored and are not committed or pushed.

HOST STARTUP AND DIAGNOSTICS

server.host loads the strict16 KiB host schema, verifies imported assets, loads
TLS/private credentials unless numeric loopback development is explicit, probes
data-directory write/fsync/delete, then creates/steps/closes a native worker.
--check performs this before any public listener. Normal start repeats the check.
Its JSON reports Python/OpenSSL/Windows/build/protocol and the native worker exit.
It proves local readiness only, not internet reachability or clean-host support.

The packaged host defaults to TLS, owner-issued credentials, four rooms and a
six-frame input window. data_dir=None deliberately disables the developer raw
bootstrap/input/rejected-packet/snapshot captures. HostAudit retains local JSONL
event logs with configurable byte/file caps, no uploader and high-frequency
events omitted unless diagnostic_audit:true. Native callbacks remain bounded to
256 messages of at most16384 decoded characters each. The existing developer CLI
keeps its separate detailed capture workflow.
