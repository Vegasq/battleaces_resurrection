CONCLUSION
Native custom games are feasible without a new replacement UI. The client
already has a lobby manager, predicted state, member grid, host Start, invitations,
accept/decline, and native status/result presentation. The missing work is a
replacement-server presence and lobby protocol, plus a scoped roster renderer
that does not call Steam for name/status/avatar. This is more than changing a
server address or redirecting the existing two-person ready message.

Try Deck vs AI is a separate path. Native CommonPb.GameMode3 is MODE_FTUE and
mode4 is MODE_1VAI. This review does not prove which serialized UI action the
visible Try Deck button currently invokes. An observed mode3 must not be renamed
AI without resolving that asset callback or recording the actual clicked flow.

NATIVE CUSTOM LOBBY FLOW (STATICALLY OBSERVED)
1. CustomGameLobbyManager.EnterLobbyScreen 0x3cab7b0 initializes and creates a
   lobby if PredictedCustomGameLobby is absent, then raises InLobbyScreenChanged.
   CreateLobby 0x3cac420 declines pending party invites, calls
   FrontServerIntegration.CreateCustomGameLobby(mode1) at 0x3cac4bb, retains the
   returned request in _pendingCreateLobbyRequest, and creates predicted local
   state: mode1, status Open, one local host/player at slot0.
2. FrontServerIntegration.CreateCustomGameLobby 0x3e46d70 returns a
   FrontPb.CreateLobbyRequest. Front.ProcessCreateLobbyResponse 0x3e48360 installs
   native lobby/party data, updates matchmaking status, and raises LobbyCreated.
   Later Front.ProcessLobbyStateNotification 0x3e48820 installs state/permissions,
   raises LobbyStateUpdated, updates active lobby and matchmaking status.
3. CustomGameMainScreenVM 0x3cb1400 RefreshViewModel consumes manager/front data.
   HasEnoughPlayersToStart 0x3cb0190 is PlayerCount == PlayerCapacity;
   CanStartGame 0x3cb01a0 additionally requires IsLocalPlayerHost;
   CanInvitePlayer 0x3cb01c0 requires LobbyStatus Open (1).
   These are UI checks; server validation must independently enforce membership,
   host, supported mode, capacity, deck readiness and stale request rejection.
4. StartGame 0x3cb1080 INLINES manager.TryStartGame 0x3cabc60. It creates a
   LobbyStateUpdateAction with oneof15 TryStartLobbyGame and tail-calls
   manager.SendUpdateAction 0x3cac870 at 0x3cb118f. Hooking only TryStartGame
   misses this button. SendUpdateActions 0x3cad560 validates/predicts, calls
   Front.UpdateLobbyRequest(list) 0x3e46f70, then retains its returned request.
5. OnLobbyStateUpdated 0x3cac9c0 reacts to state GameStarting (5). If local
   member is a non-host player and the corresponding ready action is not already
   queued, it builds oneof16 ReadyToStartLobbyGame and sends it. Do not replace
   this handshake with silent ready-on-presence. Host starts, peer acknowledges,
   then match creation should occur only after the server validates both decks.
6. Front.ProcessCustomGameCreatedNotification 0x3e40410 chooses native loading
   mode and calls GameServerIntegration.JoinGame 0x3e53940 at 0x3e405e3, followed
   by status refresh and CustomGameCreated(error). That original JoinGame path
   is NOT automatically the replacement GameData/bootstrap path. A new adapter
   must connect this notification with the existing dedicated bootstrap exactly
   once and preserve native lobby/game lifecycle; it is an untested integration.

NATIVE INVITATIONS AND THEIR STEAM DEPENDENCIES
CustomGameInvitePlayerVM.Initialize 0x3ca92e0 initializes bindings, calls
UncappedSteamFriends.ForceFriendUpdate at 0x3ca93b9, clears pending invite UI,
subscribes FriendsChanged/PredictedLobbyChanged, and tail-calls Populate at
0x3ca95cd. OnFriendsChanged 0x3ca9820 calls ClearInvitableFriendsList0x3ca98e0
then tail-calls Populate at0x3ca983a. Release0x3ca95f0 is the native cleanup.
ForceFriendUpdate0x3e738a0 has an _isInitialized guard; do not force that flag
true merely to insert server-roster rows.

PopulateInvitableFriendsList0x3ca9b30 reads _steamFriends._sortedFriends,
excludes current lobby members, then explicitly calls
Steamworks.Friend.IsPlayingThisGame at0x3ca9e36. It also requires a non-null
FriendExtension.Environment and applies region filtering when configured.
It obtains native pooled invite item VMs, binds a FriendModel, adds them to
_inviteItems, then updates HasInvitableFriends. Therefore adding synthetic
FriendModel objects to the list alone cannot provide offline presence.

CustomGameInvitePlayerItemVM.RefreshViewModel0x3ca8960 first binds its child
FriendVM. It then evaluates region, environment, GameConnectionInfo/busy,
PartyStatus (InParty1, FeatureLocked2, Invitable3), and pending invitation state.
CannotInviteReason names: None, Environment, Region, InMatch, PendingInvite,
FeatureLocked, MissingPartyStatus. It calls native property setters for reason
and CanInvite. A scoped dedicated row renderer can retain these setters and
existing visuals, but the ordinary FriendVM refresh is not safe as-is:
FriendVM.RefreshViewModel0x3d027b0 directly/inlined calls Steam Friend.Name,
IsPlayingThisGame, SteamFriends.Internal, FriendModel.OnlineStatus, and
SteamFriends.GetLargeAvatarAsync. Hooking only FriendModel.DisplayName misses
these inlined calls. FriendModel constructor0x3cff510 calls UpdateFriendExtension
0x3cff600. Model construction/pooling and avatar omission need explicit design
and runtime qualification; this note does not endorse guessed pointer writes.

InviteToGame0x3ca8f20 reads its model's FriendExtension.PlayerHandle and
FrontHandle, then tail-calls manager.InviteToCustomGame0x3cabe80. The manager
requires Open state, creates partyType3 (CUSTOM_LOBBY) for current gameMode,
adds a pending request, and INLINES Front.InvitePlayerToPartyRequest before

Acceptance must be followed by appropriate authoritative lobby notification,
not just a synthetic accepted button state. Recipient FriendVM presentation
needs the same dedicated roster treatment as the invite-list rows.

CRITICAL ORDERING
Defer native responses to a later Unity update after the originating method has
returned. CreateLobby stores _pendingCreateLobbyRequest after the Front call;
SendUpdateActions stores _pendingLobbyUpdateRequest after its Front call;
PartyInviteReplyRequest increments _pendingInviteResponseRequests after enqueue
(0x3e4696d). Synchronous acknowledgement inside a send wrapper races this state.
Use actual server-confirmed events/snapshots and keep native callbacks on the
observed Unity thread. Requests crossing frames must be rooted or copied.

DATA/STATE NEEDED FROM REPLACEMENT SERVER
CommonPb.LobbyState: status, host handle, repeated members, gameMode, region,
try-start expiry. Member: named player handle, front handle, isHost, role,
roleSlot, cosmetics/rating. LobbyPermissions contains repeated role permissions
and hostPermissions; RolePermissions contains role and allowedActions. Native
prediction uses them, so an empty/default permission object is not sufficient.
Action oneof IDs:10 change mode,11 move member,12 promote host,13 kick member,
14 leave,15 try start,16 ready to start,17 cosmetics. Lobby status values:
0 None,1 Open,2 Full,3 Closed,4 GameReadyToStart,5 GameStarting.
GetConfig0x3cab670 supports modes1 and2 only; other modes throw. First delivery
should advertise only tested1v1 and explicitly decline unsupported operations.

Minimal server design gaps: session-wide authenticated directory independent of
two match seats; stable player IDs/display names; multiple room IDs/host/slots;
targeted invitations with accept/decline/cancel/expiry and race rules; room state
revisions and authoritative permissions/readiness/start; disconnect/leave/return
after match and rematch. An unrelated connected player must never consume an
invitation's slot or start a match merely by being present/ready elsewhere.
