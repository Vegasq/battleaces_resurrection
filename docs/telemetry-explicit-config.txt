EXPLICIT UNITY CONFIGURATION / DEVICE-INFO PATHS
Updated: 2026-10-18 UTC
Scope: build37822 Windows x64; telemetry recipe3 source, not runtime qualification.

RESULT

Disabling analytics startup and event submission does not cover every explicit
native API. QueueConfig and SendDeviceInfoInConfigRequest can serialize into
separate configuration storage while the main object is retained but unstarted.
Recipe3 adds two exact-build early false returns before those bodies execute.
Existing allocations, getters, default flags and shutdown behavior are preserved.

Both APIs already return boolean false when the main object is absent. The new
XOR EAX,EAX; RET replacements run at entry, before stack changes or acquisition
of temporary storage. They do not free an uninitialized object, skip cleanup
after allocation, invoke a collector, or redirect a request to another server.
They prevent these two entry paths; this is not proof of all telemetry removal.

API ASSOCIATION

Earlier research paired contiguous function/name arrays, but lacked their reader.
The reader is now located: fd42d0 loads the image base, then iterates102 entries.
At fd4300 it loads a function from192ff50+index*8, and at fd4311 the name from
1930280+index*8. It passes that name/function pair to registration callbacks,
including fd4348 through global1d0d5c8, then advances both using the same index.
The references use image-base displacements, explaining why a RIP-relative LEA
search alone did not locate them. Association is established by this reader;
the ultimate callback implementation and runtime dispatch were not invoked.

Index16: UnityEngine.RemoteConfigSettings::QueueConfig -> RVA1fd3a0.
Index17: UnityEngine.RemoteConfigSettings::SendDeviceInfoInConfigRequest ->1fda50.
The original metadata contains only RemoteConfigSettingsUpdated on that type;
these two managed methods are absent. No guessed managed signature or reflective
invocation is treated as validation. Boolean AL return behavior comes from the
native bodies and their ordinary false branches.

RECIPE AND VALIDATION

The source recipe has61 guards: GameAssembly42, UnityPlayer18, chrome_elf1.
Both additions use a16-byte original guard and3-byte false-return replacement.
The pure patcher verifies the entire original hash and all guards before making
an equal-length copy. Unknown or modified input is rejected. Installer atomic
backup/rollback and checksum handling remain unchanged.

The read-only observer recognizes both original/replaced sites while retaining
its full normalized-file hash check. It permits pristine/partial groups for
observation; such recognition is not permission for an active API probe. Any
future active probe must independently require the complete relevant guards,
known runtime targets/signatures and initialized main-thread object state.

Validation log: local/telemetry-explicit01-tests.txt;37 patch, installer and
package tests passed, including untouched-original verification and every byte
outside the replacements. Helper build validation is recorded in STATUS.txt.
The two new guards have not been installed or runtime tested. RUNTIME_VALIDATED
remains false. Existing recipe2 gameplay evidence must not be attributed to3.
