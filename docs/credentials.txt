OWNER-ISSUED CREDENTIAL SUPPORT / SCHEMA 1

Status
The standalone credential store and owner CLI are implemented. No existing public
protocol, server admission path, client or TLS transport is changed by this module.
It is not a claim that current network connections are authenticated or encrypted.

Sixteen logic/persistence tests passed on Windows. They explicitly mock only the
OS privacy boundary; actual file parsing, hashes, locks, fsync, atomic replacement,
concurrent threads and separate writer processes execute normally.

The real Windows protected-DACL test was separately enabled and attempted. New
private directory creation and DACL readback succeeded. Creating the first private
lock file then failed with Windows error5 (access denied) under the restricted
execution token, before any token was generated. The test reports a skip for this
observed environment limit. No permissions were weakened and no existing host
directory/security policy was changed. Full real-DACL issuance/readback remains
to be tested under the intended ordinary Windows server account before deployment.
Local ignored test summary: local/credentials-tests.json.

Owner CLI (run from the repository root)
  python -m server.credentials --store local/data/credentials issue --out local/data/credentials/player-one.credential.json --label "Player One"
  python -m server.credentials --store local/data/credentials list
  python -m server.credentials --store local/data/credentials revoke <public-invite-id>

issue requires a caller-selected local output file. Its parent must already exist
(the store constructor creates its own private directory). Existing outputs are
never overwritten. The secret is written once to that exclusively created private
file; stdout contains only public invite/player metadata. list omits both tokens
and hashes. revoke takes a public invite ID, never a token. There is no token CLI
argument or command to print a stored token. Argument-parser errors do not echo
unknown argument values, including accidentally pasted credentials.

To replace a lost/revoked credential while keeping the same player profile:
  python -m server.credentials --store local/data/credentials issue --out local/data/credentials/replacement.credential.json --player-id <existing-public-player-id>
This explicit owner action accepts only an identity already present in the store.
It creates another independent invite; revoke the previous invite separately if
it should stop authorizing. Revoked records remain so their identity can be reused.
An initial issue without --player-id always creates a new server-issued identity.

Public Python API
  store = CredentialStore(runtime_directory, lock_timeout=2.0)
  public_record = store.issue_to_file(output_path, label="", player_id=None)
  player_id = store.authenticate(token, expected_player_id=None)
  changed = store.revoke(invite_id)
  records = store.list_public()
  handoff = read_credential_file(output_path)

issue_to_file returns no secret. The handoff reader returns schema/player_id/
invite_id/token for a future launcher; never log that object. Authenticate returns
the server-bound identity, which future integration should use for saved-profile
paths. A client-supplied profile name, handoff player_id or per-match seat is not an
identity proof. expected_player_id, when supplied, must match the bound identity.

AuthenticationError has the same public message for malformed, unknown, revoked
and identity-mismatched credentials. CredentialError covers owner/configuration,
storage, lock deadline and malformed-database failures. Those errors also contain
no input payloads or tokens. A server should fail admission closed on either
category, log only an appropriate category, and keep detailed storage diagnostics
local. The API is synchronous with bounded lock waits; an async coordinator should
call it off its event-loop thread and separately bound handshake concurrency.

Revocation is visible on the next authenticate call, even through an already
constructed store instance. This module does not terminate an established session;
the eventual coordinator must define and implement its active-session policy.

Format and limits
- Token: ba1_ followed by canonical unpadded base64url of32 cryptographic random
  bytes (256 bits; exactly47 characters including prefix). No passwords or derived
  low-entropy secrets are accepted. The prefix permits future format versioning.
- Player ID: p_ plus32 random hexadecimal characters, separate from native player,
  army and seat IDs. Invite ID: i_ plus32 random hexadecimal characters.
- Database: credentials.json, schema1, at most4096 invites and1 MiB. Each record
  contains public IDs, public label, creation/revocation times and SHA256(token).
  Only the digest is stored in this database; no reversible token copy exists.
- Caller-selected handoff: schema1/player_id/invite_id/token, at most4 KiB. This
  file necessarily contains the bearer secret for transfer/launcher enrollment;
  it is distinct from the hash-only server database, even when placed beside it.
- Public label: at most96 UTF-8 bytes with no ASCII control characters. JSON
  duplicate keys, unexpected fields/types, duplicate invite IDs/digests, malformed
  Unicode, noncanonical base64, oversized files and unsupported schema fail closed.

Verification hashes the fixed-format token and uses hmac.compare_digest against
every fixed-size stored digest, including revoked entries, without early success.
Parsing, filesystem I/O and the complete authentication operation are not claimed
to have uniform timing. Rate limiting and encrypted verified transport remain
required integration work; a bearer secret must never be sent over plain TCP.

Storage and failure behavior
Default runtime location is local/data/credentials, already ignored by Git. Inside
the source tree, store/output paths are limited to existing ignored runtime roots:
local/, server/data/ and server/test-data/. Caller-selected local deployment paths
outside the source tree also work. UNC paths are rejected. No secrets or captured
credential fixtures are committed in source or tests.

On Windows, a new store directory and every file receive a protected DACL at
creation granting the current process user and SYSTEM full control. The directory
entries propagate those rights to children, while created files use explicit
protected permissions. Existing directories/files must have the expected private
DACL; they are inspected and rejected if unsuitable, never chmodded or re-ACL'd.
There is no permissive fallback for a restricted token or unavailable filesystem.
The intended Windows deployment is a local filesystem supporting these ACLs.
Other platforms use owner-only0700 directories/0600 files for source-test use;
that is not a cross-platform native-hosting support claim.

Each operation takes a private cross-process lock with a finite deadline and reads
the current database. Commits create an exclusive private temporary file in the
same directory, flush and fsync it, then atomically replace the database. A failed
replace preserves the earlier database. Existing permissions are never altered
to force a write or cleanup. Any leftover temporary file contains hashes only.

Issuance first flushes/verifies its exclusive secret handoff, then commits the
hash record. A write/commit failure removes that new handoff if possible and does
not activate the token; it never removes a pre-existing file. A process crash
between those two files can leave an unactivated handoff. They are not a single
cross-file transaction: success is reported only after the database commit. A
crash after commit leaves a usable handoff and a listable/revocable public record.
Filesystem/power-loss durability beyond the platform's fsync/replace guarantees
is not claimed. Same-account processes and privileged administrators are outside
the protection provided by these local file permissions.
