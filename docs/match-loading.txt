User requirement
Immediately show feedback after starting Try Deck vs AI or a player match. The
user currently sees an unchanged menu for5-10 seconds before gameplay appears.
Use real preparation/loading/ready states, prevent duplicate starts, and clear
the indicator on readiness, explicit cancellation or startup failure. No fake
percentage. Cold application startup is a separate issue (client-startup.txt).

Presentation
The helper owns a small nonblocking Unity Canvas and TextMeshPro status strip.
Stages read Preparing match, Waiting for the other player, Loading match and
Starting match, with animated dots. A failed attempt replaces the pending text
with a fixed readable error for10 seconds. Error text never embeds server text.
The strip does not own any game state or initiate/cancel operations. Its native
CanvasGroup and Graphics do not block raycasts. Renderer exceptions disable only
the strip and are logged; they must not stop gameplay or network cleanup.

The Model issues a monotonically increasing ticket for each accepted attempt.
Only its pending ticket can advance, succeed, cancel or fail. Duplicate begins
for the same pending source/key retain the ticket and do not rewind its stage.
A real retry after rejection gets a new ticket even if its lobby epoch is the
same. Settlement is idempotent; old callbacks cannot clear a newer attempt.

Readiness boundaries
Native main FSM holds its InGame state at+0x2e8. LoadingGameUIState.Update
RVA3dee6b0 waits for game UI loaded and Simulation.IsCatchingUp=false before
entering that state. Local map completion alone is not presentation readiness.
Practice Running is entered before local AI setup: the indicator must also wait
for bot readiness, both validated JoinArmy payloads, JoinedGame delivery and
the local simulation latch. LAN uses worldReady plus server START/running and
native InGame. Normal S35 ready=false can be an intermediate SET_DECK reply,
so it cannot cancel local start intent; explicit Cancel/deck editing can.
Custom start ownership is lobby+epoch, with operation tickets captured before
native callbacks that may reenter. Normal GameStart lobby closure must not hide
loading. Authoritative rollback/abort owns failure handling, including when a
rejected request leaves the lobby epoch unchanged or advances it.

Qualification plan and boundary

the manually accepted builds. Do not overwrite practice-auto-runtime (difficulty
helper06), custom-abort-runtime (accepted baseline AI), shutdown-client-runtime
(Custom), or secure-client-runtime (normal multiplayer).
Five authored C++ checks include ticket/notice ownership. Native AI and Custom
harnesses opt into --loading-ui. They retain actual Unity PNG captures, component
text/visibility/raycast readbacks, readiness gate logs, source hashes and process
cleanup evidence. -match-loading-smoke only requests captures after two frames;
it does not alter normal readiness or delay gameplay. Production never captures.
PNG inspection is required for rendered appearance; component readbacks alone
do not prove rendering. Automated callbacks do not prove physical mouse input.
