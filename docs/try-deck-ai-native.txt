4. NATIVE AI IS LOCAL LOGIC WITH A SEPARATE SERVICE INSTANCE

This is the main additional integration boundary beyond the tutorial proof.
GameServerIntegration.ProcessAIAssignmentNotification0x3e51780 forwards an AI
handle, armyId and sequenceId through the AIManager RequestAIWithProfile path
(inlined). RequestAIWithProfile0x3b98580 avoids duplicate army IDs, respects
_noRejoin, and calls OnAddAI0x3b98730 with AIType3 (Dll), null deck/cosmetics.
OnAddAI calls AddLocalAI0x3b99170 using current game's address/port/name and the
human simulation. A direct candidate invocation can provide the selected AI
deck/cosmetics explicitly; the native assignment route deliberately permits null.

AddLocalAI:
  - Creates LocalAIDeckSelector and LocalAIGameInstance0x3db42a0.
  - That instance REFERENCES the human Simulation in _playerSimReference+0x18;
    IGameInstance.IsOwnerOfSimulation returnsfalse (0x6d5ba0).
  - Creates its OWN ServiceManager/GameServerIntegration, with _gameSimulation
    leftnull in Init. Do not replace this with the human GameServer object.
  - Creates AIPlayerProcess, Init0x37ba0d0, schedules ProcessEnteringGame and its
    timeout coroutine, then appends the process to AIManager._aiPlayers.
  - Parses a port string with Int32.Parse even for this local logic.
  - Sets _hasDllAI=true for AIType3.

ProcessEnteringGame.MoveNext0x37bd4f0 sets the AI GameServer player handle, builds
GameConnectionInfo, then calls ordinary GameServerIntegration.JoinGame0x3e53940
at0x37bdaee. That original JoinGame can create a network channel and enqueue a
join request. Thus RequestAIWithProfile alone is NOT an offline launch routine.
The coroutine waits for HasActiveGameConnectionInfo and serverState1/2, finds the
shared Simulation's SimPlayer for its requested army, registers its sim view,
waits for HQ/world readiness, applies profile ID through SetDefaultAIOverride
0x3b93fa0 and UpdateAIRuleData0x3b96720, then starts ReadAIInputAction.
Do not skip those native state/readiness gates by jumping into a coroutine state.

There is a promising native response path for the AI service: original
ProcessJoinedGame0x3e506b0 with _gameSimulation==null takes branch0x3e50f38,
builds StaticGameData, constructs JoinArmyCommand, enqueues it at0x3e50feb and
signals ready. It does not create or shut down the human simulation in that
branch. _gameSimulation must remainnull on the AI service. This path, required
ClientConfig/connection data, null front/telemetry, and the exact join response
still need isolated runtime qualification before calling it a safe implementation.

AIManager.PlayerSimulation_GameCreatedEvent0x3b97d10 initializes the native AI
world from the game data (AICreateWorld delegate call0x3b980fb). AI data updates
and the native process remain required after creation. AIPlayerProcess.ReadUnsafe
0x37bb440 consumes DLL-produced actions and calls AI service
GameServerIntegration.EnqueueInputAction0x3e53620 at0x37bb853.

Existing local_loop.cpp is SINGLE-service: isTarget accepts only serverRoot,
tick drains only that service's command/action queues and labels them with its
human player handle. Enqueue hooks discard other services. Current tutorial
runtime evidence therefore does not establish working autonomous AI commands.

Conservative candidate bridge (new work, not yet implemented):
  a. Own one mode4 practice session, unique game handle, human/AI handles, and
     exact human/AI GameServer GC roots; keep it separate from dedicated ready.
  b. Build/merge and join the human world using existing native bootstrap.
  c. Schedule native AI creation on the observed Unity thread only after the
     shared world/AI world and the selected assets exist. Use profile17/army1.
  d. Wrap ONLY the AI coroutine's JoinGame callsite. For the exact pending local
     AI handle/session, register the AI service and synthesize its native join
     response on a later Unity update; otherwise call original JoinGame.
     AddLocalAI appends the process after RunCoroutine, so registration cannot
     assume _aiPlayers already contains it on the first synchronous callback.
     An owned pending-add scope + exact rooted PlayerGameHandle identity can
     identify it initially; verify process/instance membership before delivery.
  e. Admit both exact services into bounded input capture. Each 20Hz frame has
     separate InputActionsByPlayer entries carrying the real human and AI handles.
     Include each native JoinArmyCommand once. Push one frame into the shared
     simulation, not two ticks/worlds; update the AI service's native state without
     enabling a backend connection. Preserve deterministic ordering and counters.
  f. Verify the AI actually emits build/move/attack actions and command effects.
     A profile ID in GameData, an AI world pointer, or an advancing frame alone is
     insufficient evidence that the opponent is playing.

6. END / EXIT / RETURN MUST BE A SEPARATE PRACTICE LIFECYCLE

The established multiplayer result bridge currently requires server-authoritative
match/result identity and LAN slot assumptions. Do not blindly call it for a
local mode4 game. Native victory/defeat flow waits for EndOfGameResponse; local
practice must deliver an appropriate completed local result once, preserve mode4,
and avoid fabricated progression/currency/rating rewards. Confirm exact mode4 UI
branches in an isolated test; this pass did not validate result navigation.

Native reusable cleanup boundaries remain:
  CleanupGameState0x3e51ba0 -> SimulationShutdown0x3e68030.
  AIManager.PlayerSimulation_SimulationShutdownEvent0x3b97bf0 normally calls
    DestroyAllAI(true)0x3b9a060, then destroys its AI world and zeros _aiWorld.
    An AI smoke-test variable can suppress DestroyAllAI; do not enable it.
  Native InGame shutdown reason0 selects postgame; nonzero selects MainMenu.
  MatchResultVM.OnContinue0x3d610c0 checks empty NavigationStack and sends native
    signal2; postgame flow completion0x3def0a0 selects MainMenu.
These are static/native lifecycle boundaries, not a proven mode4 return test.
Do not promise direct restoration of the edit-deck sub-screen yet. Preserve the
selected deck, let native postgame/menu run, then observe actual screen/history.

Before reset/rejoin, stop admitting practice input, let native AI shutdown remove
its processes/coroutines, verify shared simulation/world and AI world are idle,
then release owned roots/queues. Keep dedicated presence alive but mark practice
busy (or decline invites) and prevent a simultaneous multiplayer start. Returning
to menu must not send C_READY, a lobby-ready signal, or revive the old AI identity.
Qualification sequence: edit deck -> mode4 -> exact selected human deck -> distinct
AI profile/deck -> autonomous command effects -> victory and surrender/exit ->
native result/menu -> second AI game -> ordinary multiplayer invitation/start.
Also test invalid deck, double click, cancel during asset load, network loss while
practicing, and shutdown during AI creation. No such runtime tests were run here.

The initial implementation boundary is therefore a small dedicated practice
coordinator plus two-service local input ownership and result/cleanup support,
not just enabling mode4 in ba_bootstrap::create. The original client already
contains the map, decks, AI tuning, AI DLL loop and native UI needed for that work.
