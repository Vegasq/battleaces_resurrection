EXPERIMENT CONTRACT
The client flag is -original-command-scheduling-experimental. The server must
also explicitly enable experimental_command_scheduling. Ordinary launchers
and normal server configuration retain the buffered mode by default.

Authenticated unified TLS community peers negotiate version1 before using
the mode. Both humans must negotiate;unsupported hosts,mixed peers and public
queue entry are rejected. The initial scope is Custom1v1 only. No silent
fallback to another scheduling mode is permitted.

After match START,the client drains nonempty original command/action queues
independently of authoritative frame receipt or presentation. Match-scoped
batch sequence numbers preserve order;they are not requested simulation
frames. An independent1s heartbeat distinguishes an idle player from a dead
connection. Both humans must supply their own validated JoinArmy before frame0.
The common handshake still carries input-window metadata;arrival mode does
not seed,replenish or schedule commands by those buffered frame leads.
After receiving frame0,each client sends READY74 only after applying it AND
observing its original presented-frame counter reach0. The server waits for
both33-byte(version1+match32) acknowledgments before sealing frame1,then rebases
the steady clock to now+50ms. A fixed timeout cannot be extended by heartbeats.
This avoids carrying the native first-output startup delay into the entire
match. The barrier is per match,including rematches.

The server validates complete batches,keeps bounded per-player FIFO queues,
and seals each authoritative frame before awaiting the simulation worker.
Arrivals during that await belong to a following unsealed frame. Empty turns
then progress at20Hz without waiting for per-frame idle packets. Validation,
ownership,identity,deck and size limits remain enforced. The existing native
ordered-input simulation and one-unpresented-output contract remain in force.
The experiment admits frame0 with one queued authoritative frame;
the ordinary mode retains its existing two-frame startup reserve.

This server scheduling is a reconstruction choice supported by the original
sender evidence,not recovered production server code. Different network delays
still change when players' commands reach the authoritative frame. This mode
does not promise instant input,fairness under all latency,or rollback.
